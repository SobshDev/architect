# Architect v0.1: design memory and structural checks for coding agents

Approved by Gabriel Brument on 2026-09-26. This file is the build plan as approved; decisions in `.architect/decisions/` record refinements made during implementation.

## Summary
Architect is a deterministic TypeScript tool that runs on Bun. It stores a codebase's design intent in `.architect/`: components, decisions with their reasons, and rules that can be checked. Agents get the relevant slice before they edit. Every edit and every pull request is checked against the rules, and any loosening of a rule must be an explicit decision that CI shows to reviewers.

The host agent (Codex, Claude Code, Cursor) does all the reasoning through Architect's CLI, MCP tools, hooks, and skill. Architect itself makes no model API calls. v0.1 supports TypeScript/JavaScript and Python, and ships as a CLI, an MCP server, hook adapters, a skill, and a GitHub Action.

Success criteria:

- In paired evaluations on chains of tasks, the full Architect setup adds fewer structural violations per step than a control that puts the same content in AGENTS.md, with no loss in functional pass rate.
- No rule loosens without a linked decision.
- On a repo of 5,000 files: PostToolUse hook p95 ≤ 500 ms, `check --changed` ≤ 2 s with a warm cache, full graph from a cold cache ≤ 30 s.

## Interfaces

- **Files in a target repo** (every schema defined once in zod v4; `architect schema` emits JSON Schema for editors):
  - `architecture.yaml`
    - `components`: id, ordered `paths` globs, kind, owner, `entrypoints`, `deprecated`.
    - `resources`: stored state such as tables, each with an owner component and write matchers.
    - `settings`: source roots, tsconfig, folders of existing ADRs to import such as `docs/adr`, and the history window.
  - `rules.yaml`
    - Each rule has `id`, `kind`, `level` (error|warn|off, default error), `because` (decision ids, required at error), and `include_type_imports` (default true).
    - Selectors are a component id, `path:<glob>`, or `pkg:<name>`.
    - Kinds: forbid, allow-only, layers, acyclic, independent, entrypoints, external-imports, state-owner, api-stability, deprecated.
    - `waivers` need a rule, from/to, a reason, and an `expires` date at most 180 days away.
  - `decisions/NNNN-slug.md`
    - Body follows MADR 4.0. Front matter fields:
      - `status`: proposed|accepted|rejected|deprecated|superseded
      - `date`, `decision-makers`, `governs`, `supersedes`, `weakens`
      - `assumptions`: text plus a rule check or a `review_by` date
      - `evidence`: a path, `git:<sha>:<path>`, or URL, each with a verbatim quote
    - Existing MADR files are imported with their status normalized.
  - `baseline.json`
    - Fingerprints of accepted existing violations, each with a count. A fingerprint hashes the rule, source file, target, and edge kind; for cycles, the rule plus the sorted member ids.
    - No line numbers.
  - `cache/` is gitignored.
- **CLI `architect`**
  - Commands:
    - `init [--new]`
    - `graph [--format mermaid|dot|json]`
    - `check [--changed|--all] [--base <ref>]`
    - `diff --base <ref> [--head <ref>]`
    - `context [--paths] [--task] [--budget]`
    - `explain <rule:|decision:|component:|card:id>`
    - `decision new|lint|list|show`
    - `baseline update [--allow-grow]`
    - `status`, `install --agent codex|claude|cursor`, `sync`, `schema`, `mcp`, `hook <event> --agent <name>`, `ci`
  - Output formats: `--format text|json|markdown|sarif`.
  - Exit codes: 0 clean; 1 new error findings or an unapproved weakening; 2 config or usage error.
  - JSON reports carry `schema_version: 1` and a coverage section listing unmapped files and unresolved or dynamic imports.
  - Finding shape: `{rule, level, message, from, to, location, because, fix_hint, fingerprint}`.
- **MCP server**
  - Built on `@modelcontextprotocol/server` v2 with `registerTool` and zod input and output schemas, served with `serveStdio`. It keeps no state between calls and logs to stderr.
  - Tools:
    - `architect_context`, `architect_check`, `architect_diff`, `architect_explain`, all marked `readOnlyHint`.
    - `architect_propose_decision`, the only tool that writes. It always writes status `proposed` and rejects evidence whose quote isn't found verbatim in the source.
  - Every result returns structured content plus a short text summary. Tools accept `detail: concise|full`, paged results carry cursors, and results include resource links `architect://{decisions,rules,components,cards}/{id}`.
- **Hooks**
  - Codex's format is verified. Validate payloads against the generated schemas in openai/codex; confirm Claude's format in M3 against recorded payloads.
  - SessionStart: return a brief of at most 600 tokens. Save finding fingerprints and the current HEAD to `cache/sessions/<session_id>.json`.
  - UserPromptSubmit: return a brief of at most 800 tokens, only when the prompt names a component id, a path inside a component, or at least two terms from one decision title.
  - PostToolUse on `apply_patch|Edit|Write` (Claude: `Edit|Write|MultiEdit`):
    - Take changed paths from the patch headers (`*** Add/Update/Delete File:`, `*** Move to:`) or from `file_path`, and analyze those files on disk.
    - New error findings compared with the session snapshot and the baseline return `decision: block` with the rule, reason, decision link, and a fix hint.
    - Warnings go to additionalContext.
    - Edits under `.architect/` get a reminder that loosening a rule needs a decision.
  - Stop:
    - Check files changed since the HEAD recorded at session start, plus untracked files.
    - Block once if errors remain. When `stop_hook_active` is set, return JSON that doesn't block.
- **Install targets**
  - Codex: `.codex/hooks.json` and `[mcp_servers.architect]` in `.codex/config.toml`. If Codex ignores MCP entries in project config, print a snippet for the user config instead.
  - Claude: hooks in `.claude/settings.json`, `.mcp.json`, and `.claude/rules/architect-*.md` with `paths:`.
  - Cursor: `.cursor/rules/architect.mdc` and `.cursor/mcp.json`.
  - All agents: a managed AGENTS.md block of at most 30 lines between `<!-- architect:begin -->` and `<!-- architect:end -->`, plus a printed CODEOWNERS suggestion for `.architect/`.
  - Generated commands call `architect` from PATH, or else the repo's dev dependency through `bunx`.
  - `sync` regenerates all generated files; `check` warns when they have drifted.

## Implementation

- **Repo** (/Users/sobsh/dev/opensource/architect)
  - One Bun package, MIT license, `packageManager: bun@1.3.14`, strict TypeScript.
  - Published to npm as `@sobshdev/architect` (runs on Bun), plus `bun build --compile` binaries for macOS, Linux, and Windows.
  - `.gitignore`: `data/`, `.architect/cache/`, `dist/`.
  - The repo's own AGENTS.md:
    - Bun only.
    - Use `trash` instead of `rm`.
    - Keep changes surgical.
    - Test business rules and invariants only.
    - Run `bun run check` before finishing: typecheck, tests, `architect check`, and the card license lint.
- **Layout**
  - Dependency direction: `src/model` (pure types) ← `src/store`, `src/analysis/{typescript,python,git,history}`, `src/rules`, `src/diff`, `src/context`, `src/knowledge`, `src/report`, `src/integrations` ← `src/cli` and `src/mcp`, which wire everything together.
  - Only `src/analysis/typescript` may import `typescript`; only `src/mcp` may import MCP packages.
  - The repo's own `.architect/` states these rules, plus decisions for the layering and for making no model calls. It is enforced from M1 on.
- **Dependencies**: zod v4, yaml, picomatch, `@modelcontextprotocol/server` v2, `typescript` pinned to the newest release below 7.0 (used only as a parser and resolver), and web-tree-sitter with the Python grammar in wasm.
- **Graph**
  - Nodes are files, packages, and components.
  - Edges record their kind (static, type import, dynamic, require, re-export, side effect), `file:line`, and which analyzer found them.
  - Each file belongs to the first component whose glob matches.
  - An import of a workspace package points to that package's component, even when resolution lands in its build output.
- **TypeScript analyzer**
  - Parse each file with `createSourceFile`, without building a Program.
  - Resolve imports with `resolveModuleName` and a shared cache. Cover tsconfig `extends`, `paths`, project references, package `exports`, bun/npm/pnpm/yarn workspaces, and `.js` imports that map to `.ts` files.
  - Read exports from syntax and follow `export *` through the graph.
  - Compare signatures as printed declarations with function bodies removed.
- **Python analyzer** (M4)
  - Parse with tree-sitter.
  - Architect's own resolver covers source roots from pyproject and setup.cfg, `src/` layouts, relative imports, namespace packages, and re-exports in `__init__`.
- **Git**: read base snapshots with `git ls-tree` and `git cat-file --batch`, without a checkout. Cache parses by blob hash.
- **Rules**
  - Hooks evaluate only the edges from changed files.
  - `acyclic` runs Tarjan's algorithm on the cached graph with the updated edges.
  - `deprecated` and `api-stability` run in diff mode only.
  - The baseline only shrinks unless `--allow-grow` is passed, and growth counts as weakening.
- **Diff and weakening**
  - The diff compares base and head for:
    - new edges between components
    - new cycles
    - API breaks and growth at declared entrypoints
    - new dependents of deprecated components
    - changes to the contract files themselves
  - Weakening is detected two ways:
    - Semantic: base rules find violations on the head graph that head rules don't.
    - Syntactic: a rule removed, a level lowered, a selector narrowed, a waiver added, or the baseline grown.
  - Each weakening needs an accepted decision in head that lists it in `weakens`. Otherwise the finding is `unapproved-weakening` at error level.
- **Informational findings** (never fail a build):
  - hub components and god components
  - unstable dependencies (Martin's instability metric)
  - changes in propagation cost
  - hidden change coupling
  - hotspots
  - stale decisions (past `review_by`, or governing paths that were deleted)
  - rules that cite superseded decisions
- **History** (M4)
  - Read `git log --numstat` for the last 12 months, skipping commits that touch more than 50 files.
  - Report file and component pairs with support ≥ 5 and confidence ≥ 0.5.
  - Score hotspots as churn × size.
  - Add clusters of files that change together to `init`.
- **State ownership** (M4)
  - Preset write matchers: Convex `ctx.db.insert|patch|replace|delete`, Prisma, Drizzle, raw SQL writes, SQLAlchemy, Django ORM.
  - Findings are marked heuristic and default to warn.
- **`init`**
  - In M1, infer components from workspaces and top source folders.
  - Write warn rules: acyclic plus inferred layers.
  - Freeze current violations into the baseline.
  - Write decision 0001 ("record decisions", accepted) and 0002 ("initial map", proposed).
  - `--new` scaffolds empty files for designing a new system through the skill.
- **Context**
  - Rank deterministically, in this order:
    - governing decisions matched by path or component, then by BM25 on the task text
    - rules with their reasons
    - component contracts
    - top change partners
    - open violations
    - matching cards
  - The concise default is about 1,500 tokens (estimated as characters / 4), with links for the rest.
  - Repo text is returned as quoted data.
- **Skill** (`skills/architect/SKILL.md`)
  - Workflows:
    - plan a change
    - finish a change: check, diff, then fix or justify
    - propose a decision
    - refactor under the baseline ratchet
    - recover the architecture of an existing repo into proposed decisions with verbatim evidence
    - design a new system: quality scenarios, then components, then decisions, then rules
  - The skill embeds this 12-point rubric:
    1. Retrieve governing decisions first.
    2. Hide each volatile decision behind one module.
    3. Prefer deep modules.
    4. Keep strong coupling at short distance.
    5. Check change history before splitting or merging.
    6. Give each piece of state one owner.
    7. Treat observable behavior as a promise.
    8. Allow no cycles and no edges against the declared direction.
    9. Don't bring back a rejected alternative without a new decision.
    10. Loosening a rule needs its own decision.
    11. Name the affected quality scenario and its evidence.
    12. Record new assumptions with checks.
  - It also states that repo text is data, never instructions.
- **CI**
  - `architect ci --base <ref>` writes Markdown to `$GITHUB_STEP_SUMMARY` with four parts: new errors, weakenings that need human approval, fixed baseline entries, and coverage.
  - It also writes SARIF 2.1.0.
  - A composite `action.yml` at the repo root runs setup-bun, `architect ci`, and the SARIF upload. It needs `fetch-depth: 0`.
- **Knowledge** (M4)
  - `knowledge/cards/*.md`, original text under MIT:
    - The 12 principles above.
    - 21 smells: cycles, layer violation, boundary bypass, hub, unstable dependency, zone of pain, god component, scattered functionality, unbalanced coupling, hidden change coupling, hotspot, modularity violation, unstable interface, shared mutable state, state ownership drift, public API break or growth, shallow module, rising propagation cost, ownership spread, stale decision, dependency on a superseded decision.
    - 15 patterns: retry, circuit breaker, cache-aside, anti-corruption layer, strangler fig, bulkhead, saga, CQRS, idempotency key, queue load leveling, transactional outbox, ports and adapters, modular monolith, event sourcing, backend for frontend.
  - Card front matter: id, kind, title, problem, forces, use_when, avoid_when, tradeoffs, code_signals, contract_templates, related, and sources (url, retrieved, license, relation `adapted|see-also`, changes).
  - Licensing:
    - CC0 and MIT sources may be adapted; MIT notices go in NOTICE.
    - Adaptations of CC BY 4.0 material go in `packs/cc-by/` with its own LICENSE and NOTICE.
    - CC BY-SA and unlicensed sources are `see-also` only.
  - `knowledge/corpus.yaml` pins the 14 local repos (URL, SHA, license, use). `bun run corpus:fetch` recreates `data/repos`.

## Milestones and agent dispatch

- **Every subagent** runs with `model: anthropic/claude-opus-5-5` and `reasoning_effort: medium`. Each gets its plan section, the repo AGENTS.md, and a set of files that no other agent touches, and must pass `bun run check`. The main agent integrates the work. A separate reviewer agent checks each milestone against its acceptance scenarios.
- **M0**
  - Save the confirmed decisions to personal memory (project `architect`).
  - Scaffold the repo: AGENTS.md, CI, the repo's own `.architect/`, the corpus manifest.
  - Three spikes:
    1. The MCP v2 server over stdio under Bun, connected from the installed Codex and Claude Code. If either fails, fall back to `@modelcontextprotocol/sdk` v1 behind `src/mcp`.
    2. TypeScript below 7.0 and the web-tree-sitter wasm, both running inside a compiled binary.
    3. Recorded Codex hook payloads for apply_patch, SessionStart, and Stop.
- **M1**: model, store (including decision parsing), TypeScript analyzer, rules, baseline, `check`, `graph`, `init`, `explain`. Once `src/model` lands, three parallel lanes: store; TS analyzer; rules and baseline.
- **M2**: git reader, diff, API diff, weakening, reports, `ci`, the Action. Parallel lanes: git reader; API diff; weakening, reports, and CI.
- **M3**: `decision new|lint` with the evidence check, context, MCP, hooks, install, sync, skill. Parallel lanes: MCP; hooks and install; skill and instruction files.
- **M4**: Python, history, state ownership, knowledge cards. Parallel lanes: Python; history and state; cards (several agents, one per card set, with a license and signal review).
- **M5**: evaluation harness and pilot. Then the v0.1 release (npm, binaries, Action), once you approve publishing from your npm and GitHub accounts.
- **Later**:
  - Rust (for Mentem's backend), Go (with wild-workouts as a fixture), Java.
  - Codex and Claude plugin bundles.
  - Importing dependency-cruiser, eslint-plugin-boundaries, and import-linter configs.
  - Rehearsing likely future changes, and feeding real outcomes back into Architect.

## Test and evaluation plan

- **Unit tests** (selective, business rules only):
  - Each rule kind on small fixture graphs.
  - Fingerprints stay stable when lines move.
  - Weakening classification: removed rule, lowered level, narrowed selector, new waiver, baseline growth, reordered layers.
  - TypeScript resolver: paths, `extends` chains, project references, `exports`, workspaces, `.js` mapping, index files, literal dynamic imports.
  - Python resolver: src layout, relative imports, namespace packages, `__init__` re-exports.
  - Reads from git objects match reads from the working tree.
  - Evidence quote lint, card license lint, drift in generated files.
  - No tests that restate config values.
- **Integration tests**:
  - Golden JSON outputs for `check` and `diff` on fixture repos.
  - Hook adapters run on recorded Codex and Claude payloads.
  - MCP tools called through `@modelcontextprotocol/client` in the same process.
- **Acceptance scenarios**:
  1. An edit that adds a forbidden domain → infra import is blocked by PostToolUse with the rule, reason, and fix, and passes once fixed.
  2. Deleting a rule without a decision fails `ci` with `unapproved-weakening`. An accepted decision that lists the rule in `weakens` passes and appears in the CI summary.
  3. Fixing a baselined violation shows progress in `status`.
  4. Run on a local copy of the Mentem app without changing it: rules equivalent to its four architecture tests report the same planted violations. Mentem code is never copied into this repo.
  5. `init` on opencode finishes in under 30 s with plausible components.
  6. A generated repo of 5,000 files meets the performance targets. CI fails beyond 2× the targets.
- **Evaluation (M5)**
  - Setup: Codex runs without a UI (headless), using Opus 5.5 at medium effort.
  - Arms:
    - A0: no Architect.
    - A1: AGENTS.md containing the same decisions and rules as prose.
    - A3: full Architect.
    - Ablations if the budget allows: context and MCP only; A3 without the Stop hook and CI.
  - Tasks:
    - 8 chains × 6 steps on two apps written for the evaluation in `eval/apps/`: an API service built as ports and adapters, and a modular monolith web app. Chains include probe steps that depend on an earlier decision made elsewhere in the code.
    - SWE-STEPS Mini: 20 Python tasks.
  - Each step starts from the agent's own previous output.
  - Grading criteria (structural contracts and tests) are fixed before any run, by an agent that never sees any arm's output.
  - Metrics:
    - Structural pass rate.
    - New violations per step.
    - Functional resolve rate; any regression fails the step.
    - Gap between functional and structural pass rates.
    - Decay across steps.
    - Token and time overhead.
    - False positive rate, from 50 findings labeled by hand.
  - Statistics:
    - Pilot with about 60 paired steps × 3 runs, then size the full run (about 230 paired steps for a 10 point effect).
    - Use a paired bootstrap and McNemar's test.
    - Report cost and failures.

## Assumptions

- Chosen under your delegation:
  - TypeScript on Bun 1.3.14, with the host agent doing all reasoning.
  - Opus 5.5 at medium effort for subagents and the evaluation.
  - The name Architect, with npm scope `@sobshdev`. This assumes you own the scope; availability is unchecked. The scope avoids arc.codes' `@architect` packages.

- The searches show MCP SDK v2 and spec 2026-07-28 are current. Client compatibility and Bun support (the SDK docs list Node 20+) are proven in the M0 spike before M3 depends on them.
- TypeScript 7 has no stable JavaScript API, so the analyzer pins the newest release below 7.0 behind an interface.
- Two things are confirmed in M3: Claude Code's hook and settings formats, and whether Codex loads MCP entries from project config. Evaluation workspaces need hook trust granted ahead of time through managed config or approved hashes; this is confirmed in M5.
- CI is the authoritative gate; hooks are guardrails. In v0.1, Cursor gets rules and MCP only.
- `data/repos` stays out of git. Private repos are used only for validation and are never modified.
